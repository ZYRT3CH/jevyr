# GitHub advisory mode

The repository includes a composite action and companion `pull_request_target` workflow that run Jevyr against one exact checked-out commit. The companion checks out the complete trusted runtime first, and the composite resolves that verified repository root from `github.action_path`. The integration is deliberately advisory:

- workflow permissions are `contents: read`;
- checkout credentials are not persisted;
- the running workflow definition comes from the base repository rather than the proposed merge;
- pull requests must target, and manual dispatches must run from, the repository default branch, which must itself be protected and reviewed before it is treated as executable authority;
- executable Jevyr, policy, ignore rules, and assay authority come from the exact pull-request base commit in a checkout separate from the subject;
- the proposed commit's `.jevyrignore` must be absent when the trusted base has none, or be a byte-for-byte regular-file match to the trusted base; a pull request cannot hide its own material by changing capture rules;
- the two Git roots are canonicalized, required to be disjoint, and matched to full commit object IDs;
- before dependency installation, path membership is frozen from each expected commit tree and an independent direct filesystem manifest binds raw names, lstat types, modes, lengths, hard-link counts, file SHA-256 values or symbolic-link targets, and every directory mode; the subject also receives a closed non-`.git` filesystem inventory including empty-directory presence, with source work bounded during parsing and traversal to 100,000 leaves, 500,000 directories, 600,000 visited nodes, and 1 GB;
- after a successful source check, a second closed non-`.git` runtime manifest freezes every generated executable, installed dependency, internal link target, empty directory, and other build product actually used by the daemon, CLI, and exporter, bounded during traversal to 500,000 leaves, 1,000,000 directories, 1,500,000 visited nodes, and 4 GB;
- the direct subject, source, and post-build execution manifests are reverified before daemon startup, after daemon shutdown, immediately before publication, and in the final always-run guard without consulting post-build Git metadata; Git commit/tree/index/worktree checks remain defense-in-depth diagnostics;
- the runtime's authority-bearing `.jevyr` namespace must additionally be a real link-free closed subtree with exactly its frozen pre-build file membership at every post-build boundary;
- the full subject SHA must equal `HEAD`;
- the checkout must begin and end without tracked changes or untracked/ignored worktree material, while index identity, commit, and tree are fingerprinted before and after the Case;
- no package manager, host shell, local action, cache, or host build consumes files from the subject checkout;
- the trusted build requests and verifies exact Node 24.16.0 and pnpm 10.17.1 versions; the pinned setup action, package downloads, and hosted runner remain infrastructure trust;
- build, daemon, CLI, and export-verifier processes receive allowlisted empty environments with private HOME/TMPDIR; the daemon binds a dynamically assigned loopback port;
- the Forge works in its disposable boundary;
- private daemon state and its signing key remain under runner-temporary storage;
- private and public directory overrides must be new, disjoint paths below `RUNNER_TEMP` and cannot overlap either checkout;
- the workflow exports only the immutable sealed Case, canonical Seal, Record, and terminal-closure payloads with all three DSSE envelopes, public trust material, exact IntentContract and policy descriptor, terminal status, Case-bound workflow/runtime/subject provenance, complete terminal event ledger, verified content-addressed artifacts, independent replay report, and bundle manifest;
- canonical runtime provenance is Cast before Seal as the sole `subject-2` text subject; it binds event/run identity, the workflow SHA, runtime repository/commit/tree and lockfile digest, and subject repository/commit;
- unstructured daemon/CLI/watch logs and private signing material remain in the private state directory and are never uploaded;
- export guards reject links, special files, credential-like filenames, private keys, and recognizable credential formats;
- the public directory is packed into one normalized tar only after signature checks, persisted-evidence replay, terminal closure, stable artifact closure, subject/runtime immutability, and manifest verification all succeed; the tar is itself extracted and verified before upload;
- after upload, the workflow downloads that sole archive, requires its SHA-256 to equal the pre-upload archive digest, extracts it into a fresh directory, and repeats offline bundle verification before the job can succeed;
- the finalized directory is then passed through the offline `verify-bundle` implementation with the verified key ID and exact workflow/runtime/subject SHAs, so replay and closure are proven from exported bytes rather than live-daemon state alone;
- the workflow writes only a job summary and public artifact bundle;
- the job summary and composite outputs expose the verified DSSE key ID alongside the exact workflow, runtime, and subject commits so an operator can pin it out of band;
- no comment, push, merge, branch-protection, deployment, or patch-application step exists;
- `REJECT` and `UNPROVEN` remain evidence for a human, not automatic repository authority.

Third-party checkout, Node setup, upload, and download actions are pinned to immutable commit SHAs. The comment beside each pin records the human-readable major release for maintainability; updating a pin is a separate reviewed source change.

For a pull request, the base-context companion workflow checks the proposed head into `.jevyr-subject` and the exact base SHA into `.jevyr-runtime`. The action verifies both `HEAD` values before startup. It then freezes commit-tree membership and actual filesystem identity before executing a package tool, so later `assume-unchanged` flags, `skip-worktree` flags, local filters, index replacement, or `core.worktree` redirection cannot redefine the byte invariant. Bone, effective policy, and the Assay Frontier are loaded only from `.jevyr-runtime`; explicit Frontier/legacy-plan inputs must also resolve to regular files present in the frozen runtime manifest. Because the daemon and CLI recognize conventional files below `.jevyr`, the action requires that root to be a real directory without nested symbolic links and gives it closed pre-build file-and-directory membership at every boundary; an absent namespace cannot silently become an empty directory. Build output may exist elsewhere, but it cannot become or redirect an uncommitted policy or configuration input. Subject capture necessarily reads `.jevyrignore` from the subject root, so the action first rejects links and non-files and requires its bytes and presence to match the base checkout exactly. A pull request that adds, removes, or changes `.jevyrignore` therefore fails closed for its own run; once separately reviewed and merged, that policy can govern later runs. The proposed repository is otherwise a complete frozen non-Git filesystem inventory. It cannot replace the current workflow or judge and is never run directly on the host.

The pinned checkout action requires an explicit `allow-unsafe-pr-checkout` acknowledgement when fork bytes are fetched under `pull_request_target`. Jevyr sets it only on the subject checkout. That acknowledgement does not grant execution: LFS and submodule initialization are disabled, credentials and global `safe.directory` changes are not persisted, every later host executable comes from the verified base checkout, and the subject reaches Jevyr only through its bounded snapshot/capture boundary. Because an uninitialized mode-`160000` gitlink does not contain the referenced repository bytes, the mode-aware tree converter rejects gitlinks in either checkout instead of silently judging an incomplete tree.

GitHub explicitly warns that `pull_request_target` is privileged and must not execute untrusted pull-request code. This workflow uses that event only so the proposal cannot replace the in-repository discriminator that judges it; it grants only `contents: read`, references no secrets or cache, treats the separate head checkout as hostile bytes, and rejects PRs aimed at anything except the repository default branch. That branch must be protected and reviewed because its exact commit is executable authority. This is a narrow advisory construction, not a general CI pattern or a claim of zero risk: checkout/Git parsing, Jevyr's capture boundary, and the Forge isolation still process hostile data. A `pull_request` workflow gives the proposal a safer unprivileged token context but also lets the proposal affect or skip the in-repository workflow/runtime under judgment, so it cannot provide this base-pinned evidence claim. Required authority belongs in a separately controlled workflow or service, outside the subject repository.

It does not turn an in-repository `pull_request_target` workflow into merge authority. The current PR cannot edit its own base-context run, but a workflow change that is reviewed and merged becomes policy for later PRs. `pull_request_target` must remain free of subject execution, caches, write permissions, and referenced secrets. A required decision must pin the workflow and trust root outside the judged repository, such as an organization ruleset/required workflow, a GitHub App or independently operated verifier, or a base-owned `workflow_run`-style handoff that executes on a separate trusted runner. Jevyr's included workflow deliberately makes no stronger claim.

The exact checked-out workspace is cast as a local Git subject with the full commit in `revision`; it is no longer mistaken for an `owner/repository@sha` filesystem path. The default pull-request impulse is fixed in the base workflow before Cast. A manual dispatch from the default branch may supply a different complete impulse, which is still sealed once. Before Cast, the action privately commits the CLI-normalized impulse bytes, exact canonical submission, derived seed, complete normalized intent, and expected clean Git snapshot. Before export it requires the persisted sealed Case to match all of those expectations, including `auto`, `local_only`, `sovereign`, empty undeclared constraints/assays, exactly two subjects, and snapshot times equal to `sealedAt`. It also recompiles the IntentContract from that exact intent with the trusted deterministic compiler and requires byte-equivalent canonical content, so a self-consistent substituted contract cannot redirect adjudication. The action accepts either a relative `assay-frontier` path containing the complete multi-assay `jevyr.assay-frontier/1` descriptor or the relative legacy single `forge-plan`, never both. The resolved file must remain inside the verified trusted-runtime checkout and exist before daemon startup.

The complete sealed Case is exported so its identity and provenance binding can be verified offline. Consequently, a manual impulse is public proof material and must not contain a secret. The export guard still fails closed on recognizable credential formats, but pattern matching is not a substitute for keeping credentials out of workflow inputs.

## Proof bundle contract

A successful extracted bundle has this closed layout. The GitHub artifact contains exactly one tar whose contents have this shape:

```text
sealed.json
seal.json
seal.dsse.json
record.json
record.dsse.json
terminal.json
terminal.dsse.json
trust.json
intent-contract.json
policy-descriptor.json
status.json
events.json
replay.json
runtime-provenance.json
artifacts/index.json
artifacts/artifact_<24 lowercase hex>.blob  (one per index entry)
MANIFEST.sha256
```

`runtime-provenance.json` contains the exact canonical UTF-8 bytes Cast before Seal, without a trailing linefeed. It is exactly `jevyr.github-advisory-provenance/1` with `eventName`, `workflowSha`, `runtimeRepository`, `runtimeSha`, `runtimeTreeOid`, `runtimeLockDigest`, `subjectRepository`, `subjectSha`, decimal-string `runId` and `runAttempt`, and decimal-string-or-null `pullRequestNumber`. Commit/tree identifiers are full lowercase Git object IDs and the lockfile identity is `sha256:<64 lowercase hex>`.

`terminal.json` is the canonical `jevyr.terminal/1` closure with exactly `protocol`, `caseId`, `caseDigest`, `runDigest`, `lifecycle`, `stage`, `stageStatus`, `lastSequence`, `eventHeadDigest`, `recordDigest`, `artifactIndexDigest`, and `closedAt`. `recordDigest` is the SHA-256 digest of the canonical `record.json` payload, and `artifactIndexDigest` is the SHA-256 digest of the canonical complete `jevyr.artifacts/1` index. `eventHeadDigest` is null exactly for an empty ledger; `closedAt` equals the final event's `observedAt`, or the stored terminal update time only when the ledger is empty. A normal terminated Case closes at completed `terminate`, while an invalid Case closes with a failed stage. `terminal.dsse.json` signs those exact canonical bytes as `application/vnd.jevyr.terminal+json` under the same verified key as the Seal and Record.

Before publishing, the action strictly validates `sealed.json`, requires its Seal-receipt projection to equal `seal.json`, and verifies the Seal envelope. It requires exactly two sealed subjects: the exact Git source and the canonical provenance text. The provenance file's raw SHA-256, byte length, and bytes must equal the `subject-2` snapshot and locator committed by the sealed Case. The action also validates the Record and terminal envelopes against the same signer; binds Record, IntentContract, policy descriptor, Case, run, and policy version; verifies every event and cross-page prior link through the exact terminal status head, including the protocol's valid empty-ledger representation; and requires the signed terminal receipt to equal that final status, sequence and head, name the canonical Record and artifact-index digests, and carry the exact last event time. Artifact writes are closed before the receipt is signed. The action verifies every artifact's authenticated metadata, logical name, headers, length, and SHA-256 bytes, then refetches status and the artifact index to prove the closure view stayed stable; it also requires the independent persisted-evidence replay report to name the same signed Record prefix and terminal head. It then creates and checks the manifest and invokes `jevyr verify-bundle` with the verified key ID and exact provenance SHAs. That second path inventories the closed directory, revalidates the signed Case/Seal/Record/terminal chain, and independently replays the exported event, policy, IntentContract, and artifact bytes. The Record authenticates its crystallization prefix; the separately signed terminal closure authenticates the complete later tail, its exact Record selection, and the complete artifact inventory. Direct source/runtime filesystem manifests are checked again immediately before any outputs are exposed and in the final always-run guard. Finally, only a single normalized tar is uploaded; a success-only post-upload step downloads it, compares the exact archive SHA-256, extracts it fresh, and repeats `verify-bundle`.

`MANIFEST.sha256` covers every other regular file exactly once and detects corruption or accidental mixing; it is not itself a signature. `replay.json`, `status.json`, and artifact index metadata are derived convenience material and must be recomputed or checked back to the signed Seal/Record/event/digest chain by an offline verifier. The included per-run `trust.json` establishes internal signature consistency, not who operated the runner: resisting wholesale bundle replacement requires an expected key ID or artifact digest obtained from an authenticated GitHub run, or an independently pinned external trust root. A required repository decision must use that external authority. No bundle is uploaded from a failed composite action.
